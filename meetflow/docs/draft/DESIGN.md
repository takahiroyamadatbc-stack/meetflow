# Mリーグドラフト企画 設計メモ

> **このドキュメントの位置づけ**
>
> MeetFlow本体の設計書群（要件定義書・機能要件書・API設計書・DynamoDB物理設計書・Lambda設計書・画面設計書）とは**切り離して**管理する。
> 本体はMeetFlowのプロダクトコンセプト（相互非公開型マッチング／human-in-the-loop）に紐づく正式な仕様書であり、
> このドラフト企画は「麻雀コミュニティの遊び」として増築する趣味機能のため、本体の重い設計書運用には載せない。
>
> 本ドキュメントはブレスト（2026-09-17）の結論を次の実装セッションへ引き継ぐためのもの。**実装はまだ一切行っていない。**

---

## 1. 何を作るか

参加メンバー（3〜10人）でMリーグの選手をドラフト指名し、各自4人のチームを編成する。
Mリーグ2026-27レギュラーシーズンでの獲得ポイント合計で順位を競う。

Mリーグ本体のレギュレーションに倣い、**各自のチームに女性選手を必ず1人以上**組み込む。

機能は大きく2つ。

1. **ドラフト会議** — ターン制の指名、重複時の抽選、確定したチームの閲覧
2. **成績追跡** — Mリーグ公式等から結果を取得し、自分のチームの合計ポイントを表示

## 4. 決定事項

ブレストで確定した仕様。**実装者が独断で変更してはいけない。** 変更が必要ならユーザーに確認すること。

### 4.1 実施時期と集計範囲

- ドラフトは**開幕後**に実施する（シーズンは既に進行中）
- 集計は**シーズン全体**。ドラフト成立前に消化された分も遡って加算する
- 副作用として、ドラフト時点で各選手の今季成績が少し見えている状態になる（許容済み）

### 4.2 指名方式

**一斉指名＋抽選**（Mリーグ／NPB方式）。全4巡で4人のチームを編成する。

ラウンド `round`（1〜4）と、そのラウンド内の再指名回数 `wave`（1〜）の2軸で状態を持つ。
ユーザーの言う「1ターン」＝ 1つの `round` が確定するまで（wave が何回発生しても1ターン）。

```
SETUP
  ↓ 主催者が開始
NOMINATING(round=r, wave=w)   各自が1人を非公開で指名
  ↓ 全員提出 → 主催者が「開示」ボタン
REVEAL(r, w)                  一斉公開・重複を検出
  ├─ 重複なし → ラウンド確定
  └─ 重複あり → LOTTERY(r, w)
LOTTERY(r, w)                 重複選手ごとに抽選。当選者確定
  ↓ 落選者がいる
NOMINATING(round=r, wave=w+1) 落選者のみ再指名（確定済み選手は選択不可）
  ↓ ...繰り返し...
ラウンド確定 → round=r+1 へ（r=4 で COMPLETED）
```

### 4.3 女性枠ルール（動的強制）

基本は自由指名。ただし以下2つの制約がかかる。

**(a) 動的強制**

「残り巡数 ≦ 自分にまだ必要な女性数」になった参加者は、その巡から女性しか指名できない。
具体的には、3巡目終了時点で女性を1人も持っていない人は4巡目に女性強制となる。

**(b) 女流余剰枠**

```
余剰枠 B = 女性選手数(13) − 参加者数(N)
```

女性を既に確保している人が**追加で**女性を指名すると B が1減る。B=0 でブロック。

この設計で以下の不変条件が常に保たれるため、**詰みは原理的に発生しない**：

```
残り女流数 ≧ まだ女性を持っていない参加者数
```

> **証明の要点**：`残り女流数 = 未確保人数 + 残余剰枠` が初期状態で成立している。
> 必要指名は「残り女流数」と「未確保人数」を1ずつ減らし、追加指名は「残り女流数」と「残余剰枠」を1ずつ減らす。
> どちらの操作でも等式が保たれるため、残り女流数が未確保人数を下回ることはない。

したがって「女性は1人まで」という制限は**不要**。ブレスト途中でこの制限を提案したが撤回した。

参加者数ごとの余剰枠：

| 参加者 | 余剰枠 B |
|---|---|
| 3人 | 10 |
| 6人 | 7 |
| 8人 | 5 |
| 10人 | 3 |

### 4.4 余剰枠の超過は抽選で解決

一斉指名のため、同じ巡に複数人が追加指名して余剰枠を超過しうる（個別チェックは全員通るのに合計で超える）。
このときは**追加指名した人同士で余剰枠をかけて抽選**する。落選者は再指名。

結果として抽選は2種類になる：

1. **同一選手被りの抽選** — 複数人が同じ選手を指名
2. **女流余剰枠の抽選** — 別々の女流だが枠が足りない

どちらも同じくじ引き画面を流用する。

### 4.4.1 2種類の抽選の解決順

同一巡に「同一選手被り」と「女流余剰枠の超過」が同時に発生したときは、
**①同一選手被りの抽選 → ②女流余剰枠の抽選** の順で解決する。

理由は、**被り抽選に負けた人は誰も獲得していないため、余剰枠を消費すべきではない**から。
先に余剰枠抽選をやると、どのみち被り抽選で負ける人が枠を1つ食ってしまう。

```
NOMINATING(r, w) 全員提出
  ↓
REVEAL(r, w)
  ↓
① 同一選手被りの抽選 … 選手ごとに1人を当選させる
  ↓ 当選者が確定
② 確定した指名のうち「女性を既に持っている人の追加女流指名」を数え、
   余剰枠 B を超えていれば その人たち同士で抽選
  ↓
落選者（①で負けた人 ＋ ②で負けた人）が NOMINATING(r, w+1) へ
```

「①に勝って②で負ける」は起こりうるが、挙動としては正しい。
その場合も落選者として次のwaveで再指名する（扱いは①の落選者と同じ）。

### 4.5 参加人数

3〜10人。上限は `min(10, 女性選手数)` で自動バリデーションする。
2026-27シーズンは女性13人なので、実質 `40 ÷ 4 = 10人` が上限。

### 4.6 進行主体

**主催者ボタン**で進める（自動遷移しない）。MeetFlow本体のhuman-in-the-loop原則と揃える。

- 全員提出後、主催者が「開示」を押して一斉公開
- 主催者が「抽選を実行」を押してくじ引き
- **主催者は参加者を兼任できる。** ただし開示前は主催者画面にも「4/4人 提出完了」しか出さない（中身は見せない）
- 主催者画面（プロジェクター／全体進行用）と参加者画面（スマホ／指名操作用）を分ける

### 4.7 タイムアウト

**制限時間は設けない。** 主催者画面に「未提出: Bさん」を表示して催促してもらう。
どうしても連絡がつかない場合のみ、主催者が**代理指名**できる。

### 4.8 成績取得

**完全オンデマンド。** EventBridge Scheduler も定期実行Lambdaも作らない。

- 誰かがアプリにアクセスして「更新」ボタンを押したときだけ取得する
- 未取得の日だけを取りにいく。最新取得日と同じなら何もしない
- 取得は**1日1回まで**。ただし失敗時はカウントを消費しない（リトライ可）

### 4.9 日付ロジック

```
最新確定日 = date(現在時刻 − 26時間)
```

ユーザー指定の「19時〜26時は前日扱い、前日を最新日としたい」を1本の式に畳んだもの。全パターンで一致する：

| 現在時刻 | 最新確定日 | 理由 |
|---|---|---|
| 7:00 | 前日 | 前夜の対局は終わっている |
| 20:00 | 前日 | 今夜の対局は進行中 |
| 深夜1:00 | 前々日 | 昨夜の対局がまだ進行中（25時扱い） |

**境界として実際に効くのは26時（翌2:00）だけ。** 19時は最新確定日の計算を変えない（18:59でも19:01でも答えは前日）。
19時は**「対局中」バッジの表示判定**に使う値として持つこと。

### 4.10 成績データ形式

**日別結果を積み上げる。** 対局日ごとの結果を日別レコードとして保存し、合計は自前で積算する。

日別レコードは3状態を区別すること：

- `対局あり` — 結果を取得済み
- `対局なし` — その日は対局がなかった（取得済み）
- `未取得` — まだ取りにいっていない

**`対局なし` を記録しないと、対局がなかった日を永久に取りにいき続ける。**

### 4.11 配置（完全分離）

```
MeetFlowDraftStack（新規・これ1つだけ追加）
  ├─ DraftTable          専用DynamoDBテーブル
  ├─ draft_lambda        8つ目のドメインLambda
  └─ DraftApi            専用API Gateway
                           └ Cognito Authorizer → 既存User Poolを「参照」するだけ

既存5スタック（data / auth / compute / api / frontend）
  → 1行も触らない

フロントエンド
  → 既存SPAに /draft ルートを追加（git revertで戻る）
  → APIのURLは環境変数を1本足すだけ
```

**この分離が重要な理由：**

1. **撤退可能性** — gitのブランチはコードしか戻さない。デプロイ済みインフラを消すには
   `cdk destroy MeetFlowDraftStack` が要る
2. **本体の設計の純度** — READMEで押している「単一テーブル設計への忠実さ／事前に洗い出した
   アクセスパターンの上に構築」を守る。ドラフトはアクセスパターンの性質が全く違う
   （短命・イベント的・数秒間隔で状態が変わる）

**撤退手順：**

1. `cdk destroy MeetFlowDraftStack` → テーブルごと消滅
2. フロントを `main` から再デプロイ
3. ブランチを消すか放置

### 4.12 リアルタイム更新

WebSocketは使わない。**ポーリング**（TanStack Query の `refetchInterval` 2〜3秒）で十分。

ドラフトは「10人 × 30分、年1回」のイベント。ドラフト状態に `version`（単調増加のリビジョン番号）を
持たせて、変わっていなければ軽量レスポンスを返す。

くじ引きの同期演出は、サーバーが抽選結果と一緒に `revealAt`（開封時刻）を返せば、
ポーリングでも全員の画面で同じ瞬間にドラムロールを止められる。

### 4.13 参加者はコミュニティメンバーから選ぶ

ドラフトは**既存のコミュニティ機能の上に乗る**。独立した招待フローは作らない。

- ドラフトは `communityId` に紐づく。参加者はそのコミュニティのACTIVEメンバーから主催者が選ぶ
- 認証・招待・表示名・ユーザー管理は**すべてMeetFlow本体の資産をそのまま流用する**
  （`require_membership` / Cognito User Pool / 既存の招待URL）
- ドラフトの作成は他の管理操作と揃えて **OWNER / ADMIN** のみ。作成者がそのドラフトの主催者になる
- コミュニティ外の人を呼びたい場合は、先に既存の招待URLでコミュニティに入ってもらう

インフラは §4.11 の通り `MeetFlowDraftStack` に完全分離したままでよい。
参加者判定のために**本体テーブルへの読み取り権限だけ**をDraftLambdaに与える
（既存5スタックのコードは変更しない）。

### 4.14 抽選の検証可能性は操作ログのみ

サーバーが乱数を引き、`LotteryLog` に候補者・当選者・時刻を残す。それ以上はやらない。

commit-reveal（wave開始時にseedのハッシュを公開し、結果と一緒にseedを開示する）は**採用しない**。
主催者が同席する身内の遊びであり、そもそも主催者は乱数を操作できないため、
実装と画面の複雑さに見合わないと判断した。

### 4.15 集計範囲はレギュラーシーズン終了日を設定値で持つ

§1の「レギュラーシーズンの獲得ポイント合計」を守るため、
**レギュラーシーズン終了日をドラフトの設定値として持ち、その日までの節だけを集計する。**

公式サイトの日程HTMLにはレギュラー／セミファイナル／ファイナルの区別が無い（SCRAPING.md §4）。
自動判定案（`/stats` のRegularタブとの突き合わせ）は採らず、公式発表が出た時点で主催者が日付を入れる。

- 未設定のうちはシーズン全体を集計する（4月より前は差が出ないため実害が無い）
- 入れ忘れるとセミファイナルの点が混ざるので、**4月に入ったら画面に警告を出す**こと
- 2025-26シーズンの実績値は 2026-03-27（第150節）。2026-27は2027-03下旬の見込み

## 5. データモデル（実装済み）

専用テーブルなので本体のキー設計に縛られないが、本体と揃えて単一テーブル的に持つ。
以下は実装と一致している（`backend/functions/draft_lambda/handlers/repository.py`）。
実装時に `DraftPlayer`（作成時に固定する選手マスタのスナップショット）を追加した：

```
Draft            PK=DRAFT#{draftId}  SK=METADATA
DraftParticipant PK=DRAFT#{draftId}  SK=PARTICIPANT#{userId}
DraftPick        PK=DRAFT#{draftId}  SK=PICK#{round}#{wave}#{userId}
DraftRoster      PK=DRAFT#{draftId}  SK=ROSTER#{userId}#{playerId}
PlayerLock       PK=DRAFT#{draftId}  SK=LOCK#{playerId}        ← 一意制約用
LotteryLog       PK=DRAFT#{draftId}  SK=LOTTERY#{round}#{wave}#{playerId}
DraftPlayer      PK=DRAFT#{draftId}  SK=PLAYER#{playerId}   ← 作成時のスナップショット
MLPlayer         PK=MLPLAYER#{season} SK=PLAYER#{playerId}
MLGameDay        PK=MLPLAYER#{season} SK=GAMEDAY#{date}#{節番号}  ← 日別レコード
MLFetchState     PK=MLPLAYER#{season} SK=FETCH_STATE             ← 取得状況・1日1回の判定
```

**日別レコードは「選手ごと」ではなく「節ごと」にした。** 素案では
`DAILY#{date}#{playerId}` と選手単位に分けていたが、集計は常にシーズン全体を
読むため選手単位に分ける利点が無く、1節=1アイテム（8人分の着順を内包）にすると
フルシーズンで1384件→173件になる。キーに節番号を含めるのは必須で、
**同じ日付に2節入る日がある**ため日付だけでは一意にならない（SCRAPING.md §2.2）。

`MLGameDay` は §4.10 の3状態をそのまま持つ:

| 状態 | 表現 |
|---|---|
| 対局あり（取得済） | アイテムがあり `state=PLAYED` |
| 対局あり（未消化／進行中） | アイテムがあり `state=SCHEDULED` |
| 対局なし | **アイテムが存在しない** |

成績データはシーズン単位（`MLPLAYER#{season}`）でドラフト横断に持つ。
同じシーズンのドラフトが複数あっても取得は1回で済む。

**ミソは `PlayerLock`。** 「同じ選手を2人が確保する」事故を、条件付きPut（`attribute_not_exists`）で
物理的に不可能にするDynamoDBの定石パターン。

指名の受付は条件付き書き込みで「`phase=NOMINATING` かつ `round=r` かつ `wave=w` のときだけ」を担保する。
既存の `meetflow_common.transact` のパターンが流用できる。

## 7. スクレイピングの方針

### 選手マスタ

**ランタイムでスクレイピングしない。** 40人しかおらず、シーズン中はほぼ変動しない。

```
ローカルでスクレイプ → JSON生成 → リポジトリにコミット → デプロイ時にDynamoDBへシード
```

公式サイトへのアクセスは開発者が年1回叩くだけになり、規約リスクもHTML破損リスクもゼロ。

### 成績

§4.8 のとおり完全オンデマンド。1日1回上限。

**パース失敗は前提として設計すること：**

- 失敗時は古いデータを出し続けつつ、画面に「最終更新：MM/DD」を必ず出す
- ~~失敗時は既存の通知基盤で管理者にPush~~ → **やらない（確定）。**
  通知（Notification）は本体テーブルに書くエンティティで、共通の通知作成を使うと
  DraftLambdaに本体テーブルへの**書き込み**権限が必要になり、§4.11 / §4.13 で敷いた
  「本体テーブルは読むだけ」という境界を崩す。
  代わりに成績画面へ「公式サイトからの取得に失敗しています／最終更新: MM/DD」を
  常時表示する。取得はそもそも誰かが更新ボタンを押したときだけ走る（§4.8）ので、
  失敗したことはその場で押した人に分かる。Pushで非同期に知らせる必要が無い
- **手動入力のフォールバック画面を最初から作る。** これがあれば最悪シーズンは回る

### 使わないもの

- ロゴ・選手写真（著作権）。チームカラーで代替する

実装上の決定：

- **取得は `/games` への1リクエストだけ**（SCRAPING.md §6）。差分取得も
  「どの日が未取得か」の管理もしない。毎回まるごと取って上書きする
- **1日1回の判定キーは「成功した日」**。失敗時は更新しないので、パースがこけた日でも
  直ればその日のうちに取り直せる（§4.8「失敗時はカウントを消費しない」）
- **日程が1件も取れなければ失敗として扱う**。空の結果で既存データを上書きしないため
- **手動入力は公式の値で上書きされる**。公式が正で、手動はパースが直るまでの暫定
- **Lambdaは30秒・1024MB**（他ドメインは10秒・512MB）。シーズン終盤の `/games` は
  1.6MB程度あり、既定では足りない。メモリを上げているのはパース速度のため
  （LambdaはCPUがメモリに比例する）

検算（SCRAPING.md §3）は取得のたびに走らせ、食い違った選手名を警告として画面に出す。
ポストシーズンが始まると公式のRegularタブとは当然ズレるため、取得自体は失敗にしない。
