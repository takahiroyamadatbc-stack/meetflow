## 1. 使うURL

| URL | 用途 | サイズ | 取得頻度 |
|---|---|---|---|
| `https://m-league.jp/games` | 今季の対局日カレンダー＋日別結果（**主データ源**） | 約94KB（開幕直後）〜1.6MB（シーズン終盤想定） | オンデマンド |
| `https://m-league.jp/stats` | 選手別レギュラーシーズン累計（**検算用**） | 約78KB | `/games` と同時 |
| `https://m-league.jp/teams/{slug}/` | 選手プロフィール・年度別成績（マスタ生成時のみ） | 約50KB | 年1回・ローカル |
| `https://m-league.jp/{YYYY}-season/` | 過去シーズンのアーカイブ（`/games` と同一構造） | 〜1.6MB | 使わない（検証用） |

すべて **SSR済みの素のHTML**。ログイン不要、JavaScript実行不要、`curl` だけで完結する。
`wp-json` は 401 を返すのでJSON APIは使えない。

`/{YYYY}-season/` の `YYYY` はシーズン開幕年。2025-26シーズン＝ `/2025-season/`。
**今季のページは `/2026-season/` ではなく `/games`**（404を確認済み）。シーズン終了後にアーカイブへ移ると思われる。

## 2. `/games` の構造

### 2.1 対局日カレンダー

```html
<!-- 消化済み -->
<li class="p-gamesSchedule2__list js-modal2-trigger is-finish" data-target="key20260917-3">
  <p class="p-gamesSchedule2__data">9<span class="...__slash">/</span>17<span class="...__dayWeek">（木）</span></p>
  <ul class="p-gamesSchedule2__logos"><li><img alt="EARTH JETS"> ... 4チーム分</li></ul>
</li>

<!-- 未消化（Abemaの配信ページへのリンクでラップされる） -->
<li class="p-gamesSchedule2__list">
  <a href="https://abema.tv/now-on-air/mahjong">
    <p class="p-gamesSchedule2__data">9<span ...>/</span>18<span ...>（金）</span></p>
    <ul class="p-gamesSchedule2__logos">...</ul>
  </a>
</li>
```

判定ロジック：

| 状態 | 見分け方 |
|---|---|
| **対局あり・結果取得可** | `is-finish` があり `data-target` を持つ → 対応するモーダルから結果を読む |
| **対局あり・未消化／進行中** | `is-finish` が無い（`data-target` も節番号も持たない） |
| **対局なし** | その日付が日程リストに載っていない |

**これがDESIGN.md §4.10の3状態と正確に対応する。**
「対局なし」を別途記録する必要すらない — `/games` を1回取れば公式の対局日そのものが手に入る。

### 2.2 節番号とキー

`data-target="key{YYYYMMDD}-{節番号}"`。節番号はシーズン通しの連番（2025-26は1〜173）。

**⚠️ 同じ日付に2つの節が入る日がある。** 2025-26シーズンでは131日の対局日のうち **42日が1日2節**（計173節）。
2026-27も9/21・9/22・9/24・9/25・9/28・9/29が既に2節編成になっている。

→ **日別レコードのキーは日付ではなく節（`{date}-{no}`）にすること。**
日付をPKにすると1日2節の日で上書き事故が起きる。表示のときに日付で寄せればよい。

未消化の li は節番号を持たないため、**節番号はモーダル（＝消化済み）からしか取れない**。
未消化日の識別は日付＋その日の何件目かで行う。また未消化 li の日付テキストには年が入らないので、
シーズン（9〜12月＝開幕年 / 1〜5月＝翌年）から補う。

### 2.3 結果モーダル

```html
<div class="c-modal2" id="js-modal-key20260917-3" hidden>
  <div class="p-gamesResult__date">9/17<span class="...__dotw">(木)</span></div>
  <div class="p-gamesResult__number">第1回戦</div>
    <li>
      <div class="p-gamesResult__rank-badge is-1">1</div>
      <div class="p-gamesResult__name">本田朋広</div>
      <div class="p-gamesResult__point">56.7pt</div>
    </li>
    ... 4人分
  <div class="p-gamesResult__number">第2回戦</div>
    ... 4人分
</div>
```

- 1節＝2半荘（`第1回戦` / `第2回戦`）、1半荘＝4人。2025-26アーカイブ173節すべてで 2半荘×4人＝8行を確認
- **マイナスは `▲` 表記**（`▲48.8pt`）。`-` ではない
- ポイントは小数第1位まで
- 各半荘の末尾に牌譜ビューアへのPOSTフォームがあり、`data-game-id="L001_S025_0001_01A"` という
  **半荘単位の安定ID**を持つ。日付＋回戦より確実なキーになるので、日別レコードの識別子に使える

**⚠️ 文書内で最後のモーダルだけは閉じボタンの markup が無い。**
`<button class="c-modal2__close">` を終端にして正規表現を書くと **最新の1節を取りこぼす**
（2025-26アーカイブで173節中172節しか取れない事象として実測）。
終端は「次のモーダルの開始」または「文書の終わり」で取ること。
**取りこぼすのは常に最新の節** — つまり一番見たい日が消えるので、この点は必ず踏襲すること。

### 2.4 カレンダーの公開範囲

`/games` には**その時点で公式が公開している月までの日程**しか載らない（2026-09-18時点では9月分の16節のみ）。
過去〜当月は常に公開済みなので、「過去日に対して対局なしと判定する」用途では問題にならない。
未来日について「対局なし」と断定してはいけない。

## 3. `/stats` の構造（検算用）

チーム見出し → `選手名` 行（4名） → `試合数` `総局数` `ポイント` … と19指標が続くテーブル。
`ポイント` 行がレギュラーシーズンの累計ポイント。

- タブは `Regular` / `Semi Final` / `Final` の3つ。**ポストシーズンのタブはHTMLコメントアウトされており、
  その時期が来ると出現する**と思われる（2026-09-18時点ではRegularのみ）
- 選手名は `石井 一馬` のように**姓名の間にスペースが入る**。`/games` 側は `石井一馬`。
  **突き合わせの前に空白除去の正規化が必須**

### 検算結果（2026-09-18、3節消化時点）

日別積算と `/stats` の累計ポイントを24名全員で突き合わせ → **全員一致（誤差 0.0）**。
未出場16名も `/stats` 側に0として存在することを確認。

再実行は `python3 scrape_prototype.py`。不一致があれば非ゼロで終了する。

## 4. レギュラーシーズンとポストシーズンの切り分け

**DESIGN.md §1 は「レギュラーシーズンでの獲得ポイント合計」で競うと定めているため、
セミファイナル・ファイナルの分を混ぜてはいけない。**

2025-26シーズンの実績：

| シリーズ | 節番号 | 日付 |
|---|---|---|
| レギュラーシーズン | 1〜150 | 2025-09-15 〜 **2026-03-27** |
| セミファイナル | 151〜165 | 2026-04-06 〜 2026-04-30 |
| ファイナル | 166〜173 | 2026-05-04 〜 2026-05-15 |

**日程リストのHTML自体にはシリーズの区別が無い**（class も属性も同一）。切り分け方の候補：

1. **`/stats` の Regular タブとの突き合わせ（推奨）** — 日別積算が Regular 累計と一致する最大の
   プレフィックスがレギュラーシーズン。設定値が要らず自己修正する。§3の検算をそのまま流用できる
2. ファイナルは `/games` の「ファイナルシリーズの試合結果」セクションに別掲されるので識別可能
3. レギュラー終了日を設定値で持つ（発表され次第・要メンテ）

→ 1を主、3をフォールバックにするのが妥当。**実装前にユーザー確認が必要な論点**（DESIGN.md §6.2へ追記済み）。

## 5. `/teams/{slug}/`（選手マスタ用）

チーム概要＋監督＋選手ごとに以下が載る：

- 年齢 / 出身地 / プロ歴 / タイトル歴
- 年度別成績テーブル：`個人スコア` `平均打点` `4着回避率` `最高スコア` `半荘数` × 2018〜2025シーズン

`players_2026-27.json` の `stats.lastSeasonPoints` / `lastSeasonRank` / `careerPoints` はここから埋められる。

**所属団体（`organization`）は公式サイトに無い。** mj-news.net にも団体表記は無く、監督・企業名のみ。
別途手入力するか、項目自体を落とすか要判断。

### teamId と公式slug（解消済み）

`players_2026-27.json` の `teamId` は当初 公式の `/teams/{slug}` と3つずれていた
（`beastx`/`beast`、`mfc`/`fightclub`、`sakuranights`/`sakuraknights`）。
**公式の綴りに揃えたので、`teamId` をそのままURLに使える。**

## 6. 取得戦略への含意（DESIGN.md §4.8 / §4.10 への提案）

§4.8「未取得の日だけを取りにいく」「1日1回まで」という方針自体は変えないが、
**`/games` 1枚に全節が載っているため、実際の取得は毎回1リクエストで済む**。

- 差分取得のための「どの日が未取得か」という管理が不要。毎回まるごと取って上書きすればよい
- 「初回押下者が数日分待たされる」（§6.2）という懸念も消える。常に1リクエスト
- ページサイズはシーズン終盤で1.6MB程度（2025-26アーカイブの実測値）。Lambdaで扱って問題ない
- 日別レコードを保存する意味は残る（差分表示・「今日の獲得ポイント」・公式ページ破損時の履歴保全）

## 7. 規約・robots.txt

- `robots.txt`：`Disallow: /wp/wp-admin/` のみ。**今回使うページはすべて許可対象**
- 会員利用規約 第5条：禁止事項に **「本サービスによって得られた情報を商業的に利用する行為」** がある。
  身内の遊びとして非商業で使う限りは抵触しない。**公開・収益化する場合は要再検討**
- 規約は「会員（登録ユーザー）」向けの利用規約であり、公開ページの取得自体を禁じる条項は見当たらない
- 取得頻度は §4.8 の通り極小（1日1回・オンデマンド）。負荷面の懸念はない
- ロゴ・選手写真は使わない（DESIGN.md §7）。取得もしない
